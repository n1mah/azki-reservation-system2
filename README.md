# Reservation System

سرویس رزرو نوبت که در آن **سیستم خودش نزدیک‌ترین زمان خالی را پیدا و رزرو می‌کند**. طراحی حول یک مسئله شکل گرفته: وقتی صدها کاربر هم‌زمان درخواست می‌دهند، چگونه از رزرو دوگانه جلوگیری کنیم بدون آن‌که همه پشت یک قفل صف بکشند؟

| | |
|---|---|
| **راهکار هم‌زمانی** | `SELECT ... FOR UPDATE SKIP LOCKED` — بدون صف‌کشیدن |
| **پرفورمنس** | p(95) = ۴۰ میلی‌ثانیه با ۱۰۰ کاربر هم‌زمان، روی جدول یک‌میلیونی |
| **تست** | تست : ۱۴ تست در سه سطح، شامل دو تست هم‌زمانی روی مای اسکیوال واقعی |
| **استک** | Java 25 · Spring Boot 4.1 · MySQL 8 · Redis 7 · Docker |

### ساختار پکیج‌ها

```
com.azki.reservation

├── repository     UserRepository · AvailableSlotRepository · ReservationRepository
```

قواعدی که در سراسر پروژه رعایت شده‌اند:

- کنترلر هرگز مستقیماً به ریپازیتوری دسترسی ندارد و هیچ منطق تجاری در آن نیست
- موجودیت هرگز مستقیماً در پاسخ API بازنمی‌گردد؛ همیشه از طریق مپر به DTO تبدیل می‌شود
- مدیریت خطا در یک نقطه‌ی واحد است، نه پراکنده در کنترلرها
- تزریق وابستگی از طریق سازنده انجام می‌شود، نه فیلد

### مدل داده

سه جدول: `users`، `available_slots`، و `reservations` .

نکته‌ی طراحی در `reservations`:

```sql
active_slot_id BIGINT GENERATED ALWAYS AS
    (CASE WHEN status = 'ACTIVE' THEN slot_id ELSE NULL END) STORED,
CONSTRAINT uq_active_slot UNIQUE (active_slot_id)
```

قید یکتایی روی این ستون تولیدشونده است، نه روی `slot_id`. چون MySQL چند مقدار `NULL` را در ایندکس یکتا مجاز می‌داند، هم‌زمان دو تضمین حاصل می‌شود: هر زمان حداکثر یک رزرو فعال دارد، و پس از لغو همان زمان دوباره آزاد می‌شود.

### تنظیمات مؤثر بر پرفورمنس

| تنظیم | اثر |
|---|---|
| ایندکس `(is_reserved, start_time)` | جلوگیری از اسکن کامل جدول در کوئری اصلی |
| `open-in-view: false` | اتصال دیتابیس فقط در لحظه‌ی نیاز اشغال می‌شود، نه در کل چرخه‌ی درخواست |
| `HikariCP` با اندازه‌ی تنظیم‌شده | جلوگیری از فشار بی‌مورد بر دیتابیس |
| `rewriteBatchedStatements=true` | ارسال عملیات دسته‌ای در یک بسته‌ی شبکه |

## تصمیمات کلیدی

### کوئری خام به‌جای انتزاع JPA

سه رویکرد برای جلوگیری از رزرو دوگانه بررسی شد:

| رویکرد | نتیجه |
|---|---|
| `SELECT` سپس `UPDATE` | فاصله‌ی بین خواندن و نوشتن، امکان رزرو دوگانه می‌دهد |
| `SELECT ... FOR UPDATE` | درخواست‌ها پشت یکدیگر صف می‌کشند؛ الزام ۱۰۰ میلی‌ثانیه نقض می‌شود |
| **`SKIP LOCKED`** | **انتخاب‌شده** |

با `SKIP LOCKED` هر تراکنش اگر ردیفی را قفل‌شده ببیند، منتظر نمی‌ماند و سراغ ردیف بعدی می‌رود؛ نتیجه این است که هزاران درخواست هم‌زمان هرکدام زمان متفاوتی می‌گیرند، بدون صف‌کشیدن.

این عبارت مخصوص MySQL 8 است و در انتزاع JPA معادلی ندارد — نه با متد مشتق‌شده از نام و نه با `@Lock`. تنها راه دسترسی به آن کوئری خام است.

**درباره‌ی `USE INDEX`:** بهینه‌ساز روی یک میلیون رکورد، به‌جای ایندکس اختصاصی، ایندکس Unique Constraint `(start_time, end_time)` را انتخاب می‌کرد و کارایی فیلتر به ۱۰٪ می‌رسید. راهنمای صریح ایندکس آن را به ۱۰۰٪ بازگرداند.

### سه لایه‌ی دفاعی در برابر رزرو دوگانه

| لایه | مکانیزم | پوشش |
|---|---|---|
| اول | `SKIP LOCKED` | مسیر داغ و شناخته‌شده |
| دوم | `@Version` (قفل خوش‌بینانه) | مسیرهای آینده که از کوئری قفل‌دار عبور نکنند |
| سوم | Unique Constraint دیتابیس | حتی اگر منطق برنامه نقض شود |

لایه‌ی دوم مکانیزم اصلی نیست. دلیل نگه‌داشتنش این است: قفل بدبینانه تنها تا زمانی معتبر است که همه‌ی مسیرهای تغییر داده از همان کوئری عبور کنند. اگر بعداً مسیری اضافه شود که مستقیماً یک `AvailableSlot` را بارگذاری و تغییر دهد، قفل خوش‌بینانه تغییر هم‌زمان را رد می‌کند.

### کش فقط روی مسیر خواندنی

کش روی `GET /api/reservations/available` اعمال شده، با باطل‌سازی خودکار پس از هر رزرو یا لغو (`@CacheEvict`) و عمر پنج ثانیه.

مسیر رزرو عمداً کش نمی‌شود؛ منطق `SKIP LOCKED` باید همیشه وضعیت لحظه‌ای دیتابیس را ببیند و کش‌کردن آن مستقیماً به رزرو دوگانه منجر می‌شد.

Redis به‌جای کش درون‌حافظه‌ای انتخاب شد: در استقرار چندنسخه‌ای، کش محلی یعنی هر نسخه تصویر متفاوتی از واقعیت دارد.

### ابزارهایی که عمداً اضافه نشدند

**صف پیام برای عملیات رزرو.** تضمین عدم تداخل در صف معمولاً نیازمند سریال‌سازی پیام‌های یک منبع است — همان صف‌کشیدنی که با `SKIP LOCKED` حذفش کردیم، یک لایه بالاتر. ضمن آن‌که صورت‌مسئله پاسخ فوری با جزئیات زمان رزروشده می‌خواهد، و الگوی صف ذاتاً غیرهم‌زمان است. جایگاه درست صف، اطلاع‌رسانی **پس از** رزرو موفق است.

**Flyway.** برای یک نسخه‌ی اولیه‌ی schema، اجرای مستقیم `schema.sql` کافی است و اسکریپت طوری نوشته شده که قابل اجرای مجدد باشد. ارزش Flyway از لحظه‌ای است که مهاجرت‌های متوالی لازم شود.

### امنیت

احراز هویت با JWT و بدون نگه‌داری نشست سمت سرور. رمزها با BCrypt هش می‌شوند. پیام خطای ورود ناموفق برای «کاربر ناموجود» و «رمز اشتباه» یکسان است تا نام‌های کاربری موجود قابل‌کشف نباشند.

## تست‌ها

| سطح | فایل | تعداد | آنچه اثبات می‌کند |
|---|---|---|---|
| واحد | `ReservationServiceTest` | ۵ | منطق رزرو و لغو، بررسی مالکیت، رفتار idempotent |
| هم‌زمانی | `ReservationConcurrencyIntegrationTest` | ۱ | ۵۰ کاربر، ۱ زمان: دقیقاً یک برنده |
| هم‌زمانی | `ReservationThroughputIntegrationTest` | ۱ | ۵۰ کاربر، ۵۰ زمان: همه موفق، همه با زمان متمایز |
| یکپارچگی | `ReservationApiIntegrationTest` | ۷ | مسیرهای HTTP، احراز هویت، اعتبارسنجی |

دو تست هم‌زمانی مکمل یکدیگرند: اولی اثبات می‌کند رزرو دوگانه رخ نمی‌دهد، دومی اثبات می‌کند وقتی موجودی کافی است هیچ‌کس بی‌جهت رد نمی‌شود. هر دو از `CountDownLatch` استفاده می‌کنند تا ۵۰ ریسه دقیقاً هم‌زمان شلیک شوند.

تست‌های یکپارچگی روی MySQL واقعی (Testcontainers) اجرا می‌شوند، نه دیتابیس درون‌حافظه‌ای؛ چون `SKIP LOCKED` رفتاری مخصوص MySQL است و شبیه‌سازی آن نتیجه‌ی گمراه‌کننده می‌دهد.

## سنجش پرفورمنس

سنجش روی **۱٬۰۰۰٬۰۱۰ رکورد** در جدول `available_slots` انجام شد.

### نقشه‌ی اجرای کوئری

```
type: range                        ← اسکن کامل جدول رخ نمی‌دهد
key: idx_slots_reserved_start      ← ایندکس اختصاصی استفاده می‌شود
filtered: 100.00                   ← تمام ردیف‌های خوانده‌شده مفیدند
```

زمان خالص کوئری روی این حجم: **حدود ۱۶ میلی‌ثانیه**.

### بار هم‌زمان

| کاربر هم‌زمان | p(95) | نرخ خطا | توان عملیاتی |
|---|---|---|---|
| ۲۰ | ۲۵.۵ ms | ۰٪ | ۱۷۶ req/s |
| ۵۰ | ۱۶.۱ ms | ۰٪ | ۴۵۴ req/s |
| **۱۰۰** | **۴۰.۷ ms** | **۰٪** | **۸۶۲ req/s** |
| ۲۰۰ | ۱۴۵.۹ ms | ۰٪ | ۱۳۵۱ req/s |

تا ۱۰۰ کاربر هم‌زمان، الزام «زیر ۱۰۰ میلی‌ثانیه» با فاصله‌ی امن رعایت می‌شود. در ۲۰۰ کاربر از این سقف عبور می‌کنیم، اما نرخ خطا در تمام سطوح صفر می‌ماند؛ سیستم کند می‌شود ولی هرگز پاسخ نادرست نمی‌دهد.

محیط سنجش یک لپ‌تاپ توسعه با ۸ گیگابایت حافظه بود که MySQL، Redis، اپلیکیشن و خود ابزار سنجش را هم‌زمان میزبانی می‌کرد.

### ⚠️ برای بازتولید: اولین اجرا را نادیده بگیرید

اجرای نخست k6 نتیجه‌ی گمراه‌کننده می‌دهد، چون سه هزینه‌ی یک‌بار مصرف دارد: کامپایل تدریجی کد توسط JVM، پرشدن استخر اتصال HikariCP، و بارگذاری ایندکس یک‌میلیونی در بافر پول دیتابیس.

تفاوت در عمل — همان بار، همان کد:

| اجرا | p(95) | حداکثر |
|---|---|---|
| اول (سرد) | ۱۸۷ ms | ۸۵۳ ms |
| دوم (گرم) | ۲۸.۵ ms | ۱۴۳ ms |

روش درست:

```bash
# دور گرم‌کردن — نتیجه‌اش را دور بریزید
k6 run --vus 20 --duration 10s loadtest/reservation-load-test.js

# سنجش‌های رسمی
k6 run --vus 20  --duration 20s loadtest/reservation-load-test.js
k6 run --vus 50  --duration 20s loadtest/reservation-load-test.js
k6 run --vus 100 --duration 20s loadtest/reservation-load-test.js
```

اسکریپت دو آستانه دارد: تأخیر (`p(95)<100ms`) و نرخ خطا (`rate<0.01`). آستانه‌ی دوم عمدی است — سیستمی که سریع پاسخ می‌دهد اما نیمی از درخواست‌ها را رد می‌کند، قبول نیست.

### بازتولید داده‌ی یک‌میلیونی

```sql
SET SESSION cte_max_recursion_depth = 1000000;
INSERT INTO available_slots (start_time, end_time, is_reserved)
WITH RECURSIVE seq AS (
    SELECT 1 AS n UNION ALL SELECT n + 1 FROM seq WHERE n < 1000000
)
SELECT
    DATE_ADD('2027-01-01 00:00:00', INTERVAL n HOUR),
    DATE_ADD('2027-01-01 01:00:00', INTERVAL n HOUR),
    FALSE
FROM seq;
```

## نکات قابل بهبود

| مورد | توضیح |
|---|---|
| **Flyway** | مدیریت نسخه‌بندی‌شده‌ی تغییرات دیتابیس |
| **Idempotency Key** | مدیریت درست تلاش مجدد کلاینت پس از قطعی شبکه |
| **انتشار رویداد با RabbitMQ** | پس از رزرو موفق، غیرهم‌زمان و بدون تأثیر بر زمان پاسخ |
| **Rate limiting** | محدودسازی نرخ درخواست روی مسیر رزرو |
| **مدیریت اسرار** | کلید JWT اکنون از متغیر محیطی خوانده می‌شود اما مقدار پیش‌فرض توسعه دارد |
| **صفحه‌بندی** | روی مسیر لیست زمان‌های خالی، در صورت نیاز به بیش از ۲۰ رکورد |
